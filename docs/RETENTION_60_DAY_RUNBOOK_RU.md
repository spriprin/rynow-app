# RYNOW: 60 дней хранения — staging

Актуально на 8 октября 2026 года. Эта инструкция относится **только** к Supabase staging project ref `orkkwgxuzudawiailyen`. Production не менялся.

## Правило

- Данные Room, включая участников, показы, Interests, Matches, чат, жалобы, блокировки и уведомления, удаляются через 60 дней после `rooms.ends_at`.
- Анонимный гостевой аккаунт и файлы его аватарки удаляются после 60 дней без входа или изменения профиля, **только когда** больше нет его участия в Room, Match, жалобе, блокировке или уведомлении. Постоянные organizer/admin-аккаунты этим заданием не удаляются.
- Старые отдельные жалобы, блокировки и уведомления без Room удаляются через 60 дней после создания.
- Это не выполнение кнопки **Delete my data**. Она пока создаёт заявку на ручной разбор. Удаление по запросу, с сохранением общей переписки для второго участника под именем «Deleted user», требует отдельной операции и проверки.

## Как устроено

`20261008161930_retention_60_days.sql` выставляет все три значения хранения в 60, добавляет защищённые процедуры и ежедневное задание `rynow-retention-daily` на 03:17 UTC. `retention-cleanup` — серверная Supabase Edge Function. Задание отправляет ей случайный токен из Vault; ключ с повышенными правами берётся только из встроенной серверной среды функции, не из браузера, репозитория или локального теста. Публичный и гостевой роли не имеют права исполнять процедуры очистки.

Процедура сначала удаляет Room и связанные записи, затем удаляет объекты в private Storage bucket `avatars` через Storage API и лишь после этого удаляет анонимный Auth account. Ошибка на фотографии останавливает удаление соответствующего аккаунта, чтобы можно было повторить попытку на следующем запуске.

На staging оба переключателя, `private.pilot_settings.cleanup_enabled` и `private.retention_worker_config.enabled`, включены. Конфигурация URL и случайный токен созданы только на staging и не записаны в Git. На новой среде миграция оставляет очистку выключенной до отдельной настройки.

## Что проверено

- Миграция применена только к staging; все три срока равны 60 дням, cron job один.
- Запрос без токена к Edge Function вернул HTTP 401.
- Внутренний вызов по Vault-токену вернул HTTP 200 с нулевыми удалениями; реальных данных старше 60 дней не было.
- Транзакционный тест с созданным старым Room удалил его жалобу, блокировку и уведомление; тест был полностью откатан, фикстур в базе нет.
- `anon` и `authenticated` не могут исполнять процедуры удаления, `service_role` может.
- Security Advisor после миграций показывает 0 `ERROR`. Два новых `WARN` для таблиц `cron.job` и `cron.job_run_details` относятся к установленному Supabase Cron: роли `anon`/`authenticated` не имеют `USAGE` на схему `cron`, несмотря на внутренние table grants. Остальные предупреждения об анонимных гостях, намеренно доступных identity-checked RPC и платной leaked-password protection описаны в общем handoff; новых открытых retention-RPC для гостей Advisor не обнаружил.
- Локальные тесты, проверка типов, lint и сборка прошли до обновления страницы Privacy; повторная проверка обязательна перед коммитом.

Не проверено end-to-end: физическое удаление тестового аватара и анонимного Auth account. Реальный staging CAPTCHA отверг стандартный фиктивный токен; защиту не выключали и существующего гостя ради теста не удаляли. До production этот сценарий надо пройти с новым тестовым гостем, настоящим Turnstile и фотографией.

## Проверка и аварийная остановка

Сначала проверять только staging: `private.pilot_settings`, `cron.job`, ответы `net._http_response`, Edge Function logs и отсутствие просроченных Room. Не выводить Vault token или серверный ключ. Если заметна ошибка, **на staging** выставить `cleanup_enabled=false`; это остановит и планировщик, и процедуры. Не удалять cron job или Storage объекты вручную без расследования.

Перед переносом в production нужны: бэкап и инвентаризация старых данных, полный тест гостевого удаления с настоящей CAPTCHA, проверка предупреждений Security Advisor, согласованное обновление Privacy/Terms и frontend, проверка владельцем на телефонах и отдельное явное разрешение на production-миграцию/выпуск. Нельзя направлять основной домен на staging.
